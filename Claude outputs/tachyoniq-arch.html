What UADA is today

A 10-phase conversational analytics pipeline: NL question → intent extraction (LLM) → deterministic query planning → SQL generation (LLM) → AST-based security validation → DB execution → statistical analysis → visualisation → insight generation (LLM) → follow-up suggestions. The architecture is coherent and well-structured. Three LLM calls per query. 60 source files. Five-layer security model with an excellent AST-based SQL validator at its core.

What it must become to win

Competitive benchmarks (BIRD, Spider 2.0) show direct LLM text-to-SQL achieves 10–17% accuracy on enterprise complexity. Systems with governed semantic layers and proper orchestration reach 84–100%. The market has converged on semantic layers as the accuracy moat. No competitor owns the hybrid routing pattern (semantic layer for governed metrics + graceful LLM fallback for ad-hoc, with routing rationale surfaced to users). That is TachyonIQ's primary white space.

Security Layer

CRITICAL INVARIANT (must never be moved): SQLValidator.validate() runs INSIDE the SQL repair loop before EVERY execution attempt. Security violations cause immediate halt with no retry. This architecture is correct and must be preserved in all future refactoring.

Five-layer model

L1

Read-only credentials

Documented requirement for read-only DB account. Heuristic probe: attempts INSERT into __uada_readonly_probe__; logs warning if it succeeds. Not enforced programmatically — relies on DB-side configuration.

L2

SCL schema allowlist

SecurityPolicy.excluded_tables + per-table/column excluded: true flags. SchemaLinker security-filters retrieved tables before they enter the LLM prompt. SQLValidator receives the same allowed_tables frozenset at boot.

L3

AST-based SQL Validator — 9 rules

SQLGlot parse → rule chain: (1) empty, (2) comment injection (--, /*), (3) multiple statements, (4) non-SELECT type (12 forbidden: INSERT/UPDATE/DELETE/DROP/CREATE/ALTER/MERGE/TRUNCATE/COMMAND/TRANSACTION/GRANT/REVOKE), (5) system schema prefix (16 blocked: information_schema, pg_catalog, sys, sqlite_master…), (6) table allowlist, (7) dangerous function (32 blocked: xp_cmdshell, pg_read_file, sleep, benchmark, version…), (8) subquery depth >3, (9) LIMIT injection.

L4

Execution constraints

30s timeout (real enforcement only on SQLite via set_progress_handler — advisory-only on PG/MySQL). 1000-row cap via fetchmany(1001) + truncation. is_truncated flag in response.

L5

Prompt injection protection

4096-char question limit. Comment detection pre-parse. LLM prompts contain schema metadata and question only — never raw row data. InsightGenerator sees only pre-computed statistical summaries. AuditLogger logs SHA-256(SQL)[:16] only.

Critical Bugs Found

These will crash at runtime and must be fixed before any production use of the affected features. They do not require architectural changes — they are clean one-line or small-patch fixes.

BUG-1  discover_schema() — list vs dict

File: uada/db/connection_manager.py — DatabaseConnectionManager.discover_schema()

Symptom: AttributeError: 'list' object has no attribute 'values'

Cause: Calls raw.tables.values() but raw.tables is a list[RawTableInfo], not a dict.

Fix: Replace raw.tables.values() with raw.tables (iterate the list directly).

BUG-2  Cloud adapters — QueryExecutionResult field mismatch

Files: uada/db/adapters/snowflake.py, bigquery.py, redshift.py

Symptom: TypeError: unexpected keyword argument 'columns'

Cause: Cloud adapters construct QueryExecutionResult(columns=..., rows=...) but the dataclass in db/interface.py uses field names column_names and rows.

Fix: Change columns= to column_names= in all three adapter files.

BUG-3  Cloud adapters — RawColumnInfo field mismatch

Files: Same three cloud adapters.

Symptom: TypeError: unexpected keyword argument 'references'

Cause: Cloud adapters pass references=None but RawColumnInfo in db/interface.py uses references_table and references_column as separate fields.

Fix: Replace references=None with references_table=None, references_column=None.

BUG-4  BigQuery tempfile credential leak

File: uada/db/adapters/bigquery.py

Issue: Service-account JSON written to NamedTemporaryFile(delete=False) — file is never cleaned up. Accumulates credential files on disk.

Fix: Use a context manager or implement __del__ / lifespan cleanup to delete the tempfile after the engine is created.

BUG-5  can_see_sql RBAC not enforced

File: uada/api/routes/query.py

Issue: AuthMiddleware defines ConnectionPolicy.can_see_sql (analyst+ only) but POST /query returns the sql field to all roles including viewer.

Fix: In the query route handler, check request.state.role and set response.sql = None for viewer-role users before returning.

White-space analysis — 6 differentiator opportunities

1 — Hybrid routing UX

No competitor transparently routes between semantic-layer execution and LLM SQL, surfaces which path was taken, and explains why. This is the #1 accuracy and trust gap.

2 — Anomaly → narrative → evidence

Tellius comes closest with Kaiya Missions but has no evidence chain. No platform ships the full stack: detect anomaly → explain why → surface evidence nodes → recommend action.

3 — Ambiguity as UX feature

All platforms fail silently or ask clarifying questions in plain text. Surfacing structured ambiguity (specific alternatives, confidence scores) as interactive chips is unoccupied territory.

4 — Cross-warehouse semantic portability

Every vendor's semantic layer is locked to their warehouse. A dialect-agnostic SCL that works across PG/Snowflake/BigQuery/Redshift with one definition is a genuine moat.

5 — Scheduled autonomous investigation

Tellius has this but it's black-box. A user-configurable agent that runs a defined investigation nightly, produces an evidence-graded report, and sends a summary is completely open.

6 — Metric governance suggestion flywheel

No platform learns from ad-hoc queries to suggest new SCL metrics. When users ask the same ad-hoc question 10 times, TachyonIQ should propose formalising it as a governed metric.

Phases 6–10 — Analytical IR Design

The current AnalyticalIntent model is good but needs enrichment for the proposed architecture. Key changes: routing context, evidence graph hooks, ambiguity structured output, and metric governance signals.

Proposed AnalyticalIntent extensions

# Additions to existing AnalyticalIntent (uada/models/intent.py)

class RoutingStrategy(str, Enum):
    SEMANTIC_LAYER   = "semantic_layer"   # Metric exists in SCL → use QueryPlanner
    LLM_SQL          = "llm_sql"          # Ad-hoc, no SCL metric → use SQLGenerator
    HYBRID           = "hybrid"           # Combine SCL metric + LLM dimension

class AmbiguityOption(BaseModel):
    label: str           # "Revenue (net)" vs "Revenue (gross)"
    sql_filter: str      # Concrete filter this option applies
    confidence: float    # 0.0–1.0

class StructuredAmbiguity(BaseModel):
    field: str                      # Which field is ambiguous (e.g. "revenue")
    options: list[AmbiguityOption]  # 2–4 concrete alternatives
    question: str                   # Plain-English clarifying question

# In AnalyticalIntent, ADD:
routing_strategy: RoutingStrategy = RoutingStrategy.LLM_SQL
structured_ambiguities: list[StructuredAmbiguity] = []
governance_signal: bool = False  # True → suggest formalising as SCL metric
evidence_nodes_required: list[str] = []  # Columns to track in evidence graph

Routing decision logic

R1

Exact SCL metric match

All measures in intent.measures resolve to named SCL metrics. → SEMANTIC_LAYER. QueryPlanner builds deterministic SQL from SCL formulas. Accuracy: near 100%.

R2

Partial SCL + ad-hoc dimension

Some measures are SCL metrics, but dimensions or filters are not formally defined. → HYBRID. SCL metric formula is anchored; LLM adds the dimension layer.

R3

No SCL match

Measures not in SCL index. → LLM_SQL. Full SQLGenerator path. governance_signal=True if this query has been asked ≥3 times (tracked in ConversationStore aggregate).

User-facing routing transparency: The UADAResponse should expose routing_strategy and a brief explanation. The frontend should surface this as a small chip: "Answered via governed metric ✓" vs "Answered via AI-generated SQL". This is the trust differentiator no competitor has.

Phases 16–20 — Agent Loop Architecture

Current loop limitations

The current repair loop is LLM-2b → validator → re-execute, limited to llm_max_retries attempts. It has no diagnostic intelligence — it passes the raw DB error to the LLM without structured analysis. The result is generic repairs that often produce a valid but wrong query.

Proposed: Diagnostic Repair Agent

flowchart TD
    A[SQL fails execution] --> B[ErrorClassifier\nDeterministic rule-based]
    B --> C{Error type}
    C -->|COLUMN_NOT_FOUND| D[ColumnResolver\nFuzzy-match against SchemaContext\nSuggest correction]
    C -->|TABLE_NOT_FOUND| E[TableResolver\nCheck SCL aliases\nSuggest via schema linker]
    C -->|TYPE_MISMATCH| F[TypeCoercer\nInject CAST from column type in SchemaContext]
    C -->|SYNTAX_ERROR| G[SyntaxRepairer\nLLM repair with error + schema hint]
    C -->|TIMEOUT| H[QuerySimplifier\nRemove optional joins · inject stricter LIMIT]
    D --> I[Repaired SQL]
    E --> I
    F --> I
    G --> I
    H --> I
    I --> J[SQLValidator again MANDATORY]
    J --> K[Re-execute]

The ErrorClassifier is fully deterministic — it parses the DB error message and applies regex patterns to classify the error type before any LLM call. Column-not-found and type-mismatch errors can be repaired deterministically in most cases, saving an LLM call.

Agentic investigation loop (Phase 30 differentiator #5)

Beyond the repair loop, TachyonIQ should support a multi-step autonomous investigation agent: a user asks "Why did Q3 revenue drop?" and the agent runs a sequence of queries — trend analysis → segment breakdown → anomaly detection → hypothesis testing — assembling an evidence graph before returning a final narrative. This is distinct from the single-turn pipeline.

flowchart TD

    B --> C[Step 1: Trend query\nConfirm the drop exists]
    C --> D[Step 2: Segment breakdown\nRevenue by region, product, customer tier]
    D --> E[Step 3: Anomaly detection\nIdentify outlier segments]

Proposed additions

Root Cause Analyser — new component

The RCA engine follows a contributive decomposition approach:

  1. Metric decomposition: Use the SCL metric formula to decompose the change into additive factors (volume effect, mix effect, rate effect).
  2. Dimension contribution scoring: For each dimension column, compute the % of total metric change attributable to changes within that dimension's values.
  3. Hypothesis ranking: Sort candidate root causes by contribution magnitude × statistical confidence.
  4. Evidence queries: Generate verifying queries for top-3 hypotheses; execute and validate.

Library: dowhy (causal inference) for structural causal model, falling back to manual decomposition when causal graph is unavailable.

Enhanced time-series — STL + automatic ARIMA

Replace the fixed ARIMA(1,1,0) with:

  • STL decomposition (Seasonal-Trend using LOESS) — expose trend, seasonal, and residual components to users, not just the composite
  • auto_arima (pmdarima) — automatic order selection with AIC/BIC criterion; max order (3,2,3)
  • Prophet (Facebook) — for irregular time series with holidays/events; optional heavy dependency
  • Changepoint detection — ruptures library; detect structural breaks in time series
Contextual anomaly detection

The current Isolation Forest detects global anomalies (unusual rows in isolation). Production analytics needs contextual anomalies — a value that is unusual for the current time period or segment even if globally normal.

Proposed approach:

  • Group-aware z-score: compute z-score within each group (segment × time bucket), not globally
  • Seasonal adjustment: compare current period to same period in prior cycles before flagging as anomaly
  • ADTK library: temporal anomaly detection toolkit with persistence and quantile detectors

    EVENT        = "event"       # A known external event (e.g. product launch)
    ANOMALY      = "anomaly"     # A detected anomaly
    HYPOTHESIS   = "hypothesis"  # A candidate causal explanation
    CONCLUSION   = "conclusion"  # A confirmed or refuted conclusion

class EvidenceEdgeType(str, Enum):
    CAUSES       = "causes"      # A causes B (causal claim)
    CORRELATES   = "correlates"  # A correlated with B (statistical)
    EXPLAINS     = "explains"    # A explains B (contextual)
    CONTRADICTS  = "contradicts" # A contradicts hypothesis B

class EvidenceNode(BaseModel):
    id: str
    type: EvidenceNodeType
    label: str
    value: float | str | None = None
    confidence: float          # 0.0–1.0
    sql_query: str | None      # The query that produced this node's evidence
    row_count: int | None      # How many rows support this node

class EvidenceEdge(BaseModel):
    from_id: str
    to_id: str
    type: EvidenceEdgeType
    weight: float              # Contribution strength
    p_value: float | None      # Statistical significance where applicable

class EvidenceGraph(BaseModel):
    root_question: str
    nodes: list[EvidenceNode]
    edges: list[EvidenceEdge]
    top_conclusion: str        # One-sentence synthesis
    confidence: float          # Graph-level confidence (min of critical path)
